## CACHE_VER 未触发更新缺陷（重要工程教训）
- 现象：改了 `pwa/js/exam.js` 但 pre-commit 报 `CACHE_VER 未变`。实测 HEAD~1 实际资源哈希 `806676e364`，当前（含新 exam.js）哈希 `e315ef7bde`，而 HEAD/HEAD~1 的 sw.js 都记录 `e315ef7bde` → 版本号超前于仓库内容。
- 成因：**按指定路径部分提交** + 钩子按**工作区全量**算哈希 → sw.js 版本号可能反映未提交状态；后续真变化哈希可能恰好等于已发布值 → SW 不换缓存 → 用户看不到改动。
- 修复 `tools/build_sw.py`：① `--bump` 强制升版（`-uN` 后缀）；② 后缀保留（常规运行不回退 `-uN`→纯哈希）；③ pre-commit 自动检测（`git diff --cached HEAD` 有 PRECACHE 改动且哈希同 HEAD 值 → 自动 `-u1`）；④ 替换正则须吃掉原分号（否则 `'...';;`）。
- **判断版本号是否真会更新**：比较 `git show HEAD:pwa/sw.js` 的值与"用户端已加载值"是否相同，不能只看 build_sw 报"未变"。必要时 `python tools/build_sw.py --bump`。

## 刷新恢复位置：F5 不跳、强刷才跳（根因 + 修复）
- 现象：F5 普通刷新不会回到上次位置；Ctrl+Shift+R 强刷才会「自动跳转」到记录位置。
- 根因：**浏览器自身滚动恢复与页面 JS 定位互相覆盖**。`history.scrollRestoration` 默认 `auto`，F5 后浏览器会自行把页面滚回「刷新前的位置」（后执行者常赢，把 JS 的定位顶掉/抵消）；而 Chrome 硬性重载**不做**滚动恢复（重置到顶部），于是只剩 JS 的 localStorage 定位生效 → 看到跳转。
- 次要干扰：① SW 是 `skipWaiting + clients.claim`，F5 时新 SW 激活会 `controllerchange → location.reload()`（common.js），多一次加载让时序更乱；强刷绕过 SW（`controller` 为 null，`wasControlled=false`）不触发 reload。② 批注贴图从 IndexedDB 异步回填、KaTeX 渲染会改变文档高度，定位后还会被顶偏。
- 修复：
  - `common.js` 顶部加 `history.scrollRestoration = 'manual'`（common.js 同步加载、早于所有 defer 脚本，index/exam/good/selected 全覆盖）——滚动权收归页面自己。
  - `exam.js`：把 `restoreTopBar()/syncTopH()` 移到定位**之前**（顶栏展开会撑高文档顶偏），定位后 `requestAnimationFrame` + `load` 再校准一次。
  - `selected.js`：同样加 rAF + load 二次校准。
  - `reader.js`：新增 `applyScroll(y)`（rAF 一帧 + load 校准，`document.readyState==='complete'` 时直接补一次），`restorePos` 两处 `scrollTo` 均改用它。
- 说明：manual 后 SW 的 `location.reload()` 会从顶部开始，但 `beforeunload` 已保存位置（`curPaper`/`cur` 为空时保留旧值），reload 后仍恢复。
